Creative Project Plan · research, not a finished game

Coin Dash.

Ten seconds. Two choices.
Can you reach the next coin?

Research question: How can a resetting timer, fewer coins, and increasing distance make a simple collection game harder while preserving a fair route?

Josh chose this concept and clarified the fairness rule on November 11: at least one coin must be reachable, but the player decides which one to chase. The game does not mark the safe choice.

Inspect the fairness check ↓

The rules, in plain words.

  1. Run a simple character around one flat, obstacle-free arena using WASD or arrow keys.
  2. Start each chase with 10 seconds. Collect a coin for one point and reset the timer to 10.
  3. Start with six coins. Proposed difficulty steps: five at score 3, four at 6, three at 9, and two from score 12 onward. These thresholds still need playtesting.
  4. After collection, regenerate the layout from the character’s current position. Later coins have a larger minimum distance, capped so a fair placement remains possible. Coins stay still during each chase.
  5. At every reset, at least one coin must be reachable with reaction time allowed. The other can be risky or also reachable. Choosing poorly or taking a detour can still end the run.
  6. At zero, freeze gameplay, show the score, and offer replay. Expiry wins a same-frame tie; collecting after expiry cannot revive the run.

01 / Concept & audience decisions

Keep the action simple.
Make the choice matter.

A / Fixed 30-second collector

Collect as many coins as possible before a single timer expires. Easier to implement, but individual distance decisions have fewer consequences.

B / Coin Dash · chosen

Every collection buys another 10 seconds. Fewer, farther coins create repeated decisions. It adds a fairness constraint to test, which is the creative experiment.

Dream: a small, tense arcade game that makes players think “one more coin.” Working promise: one complete sign-in → play → save score → private history → account-update journey. Experiment: compare random placement with a placement rule that guarantees a reachable option.

Primary audience hypothesis: classmates who want short, easy-to-learn keyboard games. Alternative: competitive players who want complex movement and public rankings. Choose casual short sessions; no multiplayer, enemies, obstacles, jumps, sprinting, public leaderboard, or complex animation in the initial scope. Mobile gameplay is not promised.

02 / Original sources → technical choice

Blender makes objects.
Godot runs the game.

Sources reviewed November 11, 2026. Dates here are access dates. Documentation establishes capabilities; it does not prove this game has been built.

Movement and timer / Godot documentation

The first 3D game tutorial covers character movement, interactions, and game UI. Timer documentation confirms that starting an already running timer resets it and that expiry emits a timeout signal.

Decision: use GDScript, a simple character, and a one-shot 10-second timer. Prototype normalized movement with an overhead camera; collision collection and end-state timing need actual engine tests.

Simple models / Godot’s Blender import guide

The official 3D format guide recommends glTF and explains Blender-to-GLB export. Direct .blend import calls Blender, which must be installed.

Decision: begin with engine primitives. Later model a cube-like character and a coin in Blender and export GLB. No custom model, animation, import, or Blender installation has been verified for this project.

Browser delivery / Godot and MDN

Godot’s web export guide requires WebAssembly and WebGL 2.0, describes single-thread exports, and limits web rendering to Compatibility. It says Godot 4 C# projects cannot currently export to web. The MDN Canvas API reference describes browser graphics and distinguishes 2D canvas from WebGL.

Decision: investigate GDScript with Compatibility and a single-thread web export. A browser export smoke test is an early gate. A 2D Canvas version is the fallback if export or 3D complexity exceeds the project’s scope.

Account workflow / Django authentication

The official Django authentication guide documents users, login/logout, password management, and session behavior.

Decision: plan a Django account/score wrapper with SQLite for the small initial app. Use the framework’s password-change form and enforce ownership in every score query. Display-name editing, score validation, and account-specific access tests remain application work. GitHub Pages hosts this research only; the account app will need server hosting.

03 / Creative experiment & evidence

A fair chance.
A player’s decision.

Proposed model: 60 × 40 world-unit arena, constant speed of 5 units/second, normalized diagonal movement, no obstacles, and a 2-second reaction/turning reserve. These are tunable assumptions, not measured player behavior.

safe distance = speed × (timer − reserve)
              = 5 × (10 − 2) = 40 units
minimum spawn distance = min(30, 4 + score)
available coins = max(2, 6 − floor(score / 3))

After each collection, place one coin between the minimum distance and the 40-unit safe limit. If bounded random attempts fail, use a deterministic position toward the farthest corner inside that range. Fill the other positions with distinct coins; they can be farther away. Do not visually reveal which coin was guaranteed. Validate bounds and distances before showing the next layout.

This guarantee applies at the start of each 10-second chase. It does not mean a safe option must remain reachable after the player spends time running the wrong way. In an obstacle-free, constant-speed arena, straight-line distance is the proposed path estimate; acceleration, obstacles, or a changing camera would require a revised model.

What was actually checked?

The AI-assisted reproducible Python planning probe checks the geometry independently of Godot. With a fixed seed of 218 over 5,000 sampled layouts:

  • Random-only baseline: 162 layouts had no coin reachable under the model.
  • Guarded placement: all 5,000 sampled layouts had at least one reachable coin.
  • Additional checks: coin count never below two, increasing minimum distance, distinct in-bounds coins, 30 forced fallback cases at corners/center, and the 40-unit boundary.

Read actual output. Reproduce from the repository root: python3 programming-research/fairness_probe.py.

Limit: this is a mathematical sample, not a playable game, universal proof, engine benchmark, or human fairness test. Reaction allowance is assumed. No Godot timer, coin collision, Blender import, account, database, or browser gameplay test has run.

Next experiment: implement a flat-arena greybox and ask a partner to choose between the last two coins. Expect a deliberate straight run to the guaranteed coin to finish with time left. Record actual collection times, wrong choices, and whether distances are understandable. Increase the reserve or lower the distance cap if reaching a coin requires near-perfect movement. Stop tuning after one short review session and keep the conservative safe-distance rule as fallback.

04 / Five stories & responsibility sketch

One game.
One complete journey.

AccountPlaySave scorePrivate historyAccount update
  1. As a player, I can sign up, sign in, and sign out. Check: show useful validation errors; signed-out requests cannot access private scores or account changes.
  2. As a player, I can run, collect coins, and replay. Check: the timer starts at 10, collection adds exactly one point and resets it, placement follows the fairness/count rules, and zero ends the run once. Replay resets score and timer. Reject collection after game-over.
  3. As a player, I can save my completed run. Check: save once to the signed-in account, validate a nonnegative integer score and run data, reject malformed or repeated submissions, and retain the result after refresh and a new session.
  4. As a player, I can view my private dashboard. Check: show best score and recent runs with a useful empty state; account B cannot read or alter account A’s results, including through direct requests.
  5. As a player, I can edit my display name and change my password using my current password. Check: incorrect current password fails; changes apply only to the signed-in owner; verify the chosen session behavior after a successful password change.
